# Spirits — что надо делать в игре

Записка для игрока, **доказанная дизассемблированным кодом**. Все адреса —
**оригинальная раскладка MSX** (`SPIRITS.1` load `9000`, `SPIRITS.2` load
`82A0`, резидентный слой `D000`), то есть `disasm/msx/orig/*.asm`. Адрес
Вектора в текущей сборке = адрес MSX − `0xB700` (например `CDF9` → `16F9`).

Каждое утверждение снабжено ссылкой на процедуру или таблицу. Там, где вывод
не доказан кодом, стоит слово **предположение**.

Источники разбора: `disasm/msx/orig/{spirits1,spirits2,resident,himem}.asm`,
`docs/render-paths.md`, `docs/msx-memory.md`, `docs/msx-vdp-abi.md`,
`docs/i18n-inventory.md`, `docs/adapter-requirements.md` § 0e,
`tools/marker/extract.py` + `build/marker/data.json`, `ref/msx/orig/*.payload`.

---

## 0. Три предложения

Ты — маг; надо обойти замок из 87 комнат, найти **хрустальный шар** (без него
нижняя половина экрана не работает как «радар»), потом по его наводке —
**священную книгу** и **жезл власти**. С книгой коснись заколдованного
**доспеха**, с жезлом — заколдованной **принцессы**: оба расколдуются. Когда
расколдованы оба — застрели **орла** молнией: это конец игры.

**Главные неочевидности** (из-за них «непонятно, что делать»):

1. Клавиши `1`..`5` вообще ничего не делают, **пока не взят шар**
   (`BF83`: `ld a,(LEVEL_VARS+7) / or a / ret z`).
2. Книга и жезл **физически не появляются в комнатах**, пока не взят шар
   (`C975`: при `LEVEL_VARS+7 == 0` цикл идёт по **одному** предмету, не по трём).
3. Молния **никого не убивает**, только оглушает на ~50 кадров (`BD42`).
   Единственное исключение — орёл, и только когда оба заколдованных уже
   расколдованы (`C0AF`).
4. **Прикосновение к орлу = мгновенная смерть** (`C079` → `jp C625`), а к
   доспеху и принцессе без нужного предмета — просто ничего.
5. Комната `56` — **ловушка без выхода**: вся энергия снимается сразу (`C60D`).
6. Проценты в конце — это **не «сколько игры пройдено»**, а сумма «комнат
   посещено / 4» + 15 за каждый взятый предмет и за каждое расколдовывание
   (`CC0D`). Максимум, который можно показать, — **96 %**, не 100 %.

## 1. Цель игры и экран итога «HAS COMPLETADO EL 00% DE LA AVENTURA»

### 1.1 Когда он показывается

**Только при проигрыше** — когда кончились все жизни. Главный цикл игры
(`BB89`):

```
BB89  call CF3E / call CA3D        ; новая игра: панель, сброс всего
BB8F  call BF34                    ; один кадр игры
      ld a,(BBD4) / or a / jp nz,BCF6   ; орёл убит → ПОБЕДА
      ld a,(BF38) / cp 1 / jr z,BBA5    ; герой погиб
      call KBD_CHK (пауза H) / jr BB8F
BBA5  call CA7B                    ; звук + «минус жизнь» + гашение фигурки
      ld a,(GAME_VARS+8) / or a / jr z,BBCC   ; жизней нет → итог
      ... восстановить контрольную точку, продолжить
BBCC  call CC0D                    ; ← ЭКРАН ИТОГА С ПРОЦЕНТОМ
      call CFAA / jr BB89          ; ждать клавишу и начать заново
```

Путь победы (`BCF6`) экрана итога **не показывает**: он рисует героя образами
`0x0C`/`0x0B` в обеих половинах, играет финальную музыку (`MUS_TRACK_2`,
`BD24`) и уходит на `BB89` — новая игра. Значит «100 %» игрок не видит
никогда, даже выиграв.

### 1.2 Как считается процент — `CC0D` (`150D` на Векторе)

```
CC0D  call CFCA                     ; погасить экран
      hl=0x6000 bc=0x181F a=0x30 / call CF28   ; залить цвет всего экрана
      ld hl,F2B9                    ; карта посещённых комнат, 87 байт
      ld bc,0x5700                  ; b = 87 комнат, c = 0
CC21  ld a,(hl) / or a / jr z / inc c   ; посчитать НЕнулевые
CC26  inc hl / djnz CC21
      srl c / srl c                 ; c = посещено / 4
      ld a,(CD42) / add a,c         ; + счётчик наград
      → две десятичные цифры в TEXT_ES+0x14/+0x15 (CC33..CC4D)
CC4F  ld hl,TEXT_ES / de=0x0808 / b=0x29 / call CDF9   ; напечатать строку
```

**Формула:**

```
процент = (число посещённых комнат) / 4  +  15 × (число наград)
```

* «Посещена» = комната побывала **верхней** (игровой): `C64A` пишет `0x80` в
  `F2B9 + номер` при каждой отрисовке верхней комнаты (`C64D`).
  Комнат 87, значит первое слагаемое ≤ `87/4 = 21`.
* «Награда» — прибавка `0x0F = 15` к байту `CD42`. Мест, где она даётся,
  ровно два:
  * `CD3C` — хвост обработчиков `CD12`/`CD1F`/`CD2C`, то есть **подбор
    предмета**, 3 штуки → 45;
  * `CACF` — хвост `CAA0`/`CAAF`/`CAB7`, то есть **расколдовывание**
    (вызовы из `C079`), 2 штуки → 30.

**Максимум = 21 + 45 + 30 = 96 %.** 100 % в одной игре недостижимо —
это арифметический факт из кода, а не догадка. (Оба слагаемых обнуляются
в `CA52`…`CA66` при каждой новой игре.)

### 1.3 Сам текст

`TEXT_ES = B5E0`, 41 байт, печатается с позиции ряд 8 / колонка 8; из-за
кодов `[skip N]` ложится на три ряда экрана:

| ряд | колонки | текст |
|---:|---|---|
| 8 | 8..25 | `HAS COMPLETADO EL ` |
| 10 | 15..17 | `OO%` ← сюда пишутся цифры |
| 12 | 8..23 | ` DE LA AVENTURA ` |

Подробности кодировки и ограничения на перевод — `docs/i18n-inventory.md` § 1.2.

## 2. Устройство мира: 87 комнат, сетка 5 × 18

### 2.1 Два окна на одном экране

Экран разрезан на три зоны (`docs/render-paths.md` § A.1, § C.0):

| зона | строки Y | что |
|---|---|---|
| верхнее окно | `00..5F` | комната, где ходит герой (`GAME_VARS+0xC`) |
| нижнее окно | `60..BF` | «смотровое» окно (`LEVEL_VARS+0`) |
| панель | `C0..` (колонки 24..31) | VIDAS / ENERGIA / OBJETOS |

Обе половины рисует одна и та же процедура `D184`; бит 7 номера комнаты
добавляет смещение `0x60` (`D184`..`D18B`).

### 2.2 Запись комнаты и соседи

Таблица `ROOM_MAPS`, `8446..A79B`, 87 записей подряд, индексатор `D16C`.
Формат (`docs/render-paths.md` § A.3):

| смещение | что |
|---|---|
| `+0` | сосед **вверх** |
| `+1` | сосед **вниз** |
| `+2` | сосед **влево** |
| `+3` | сосед **вправо** |
| `+4`, `+5` | число элементов N (дважды) |
| `+6…` | N элементов по 4 байта: `[образ|бит7][Y][X][код цвета]` |

**Поправка к `docs/render-paths.md` § A.3.** Там написано «`+2` — переход при
`Y ≥ 0xE6`, `+3` — при `Y < 0xE6`». На самом деле в `C33E`..`C344` регистр
`hl` указывает на `GAME_VARS+0xB`, а это **X**, а не Y (`ld bc,(GAME_VARS+0xA)`
даёт `c` = Y из `+0xA` и `b` = X из `+0xB`, `D868` берёт `b` = X). Верно так
(`C32C`, `0F2C`):

```
X ≥ 0xA9 и X < 0xE6   → ушёл ВПРАВО:  сосед +3, X := 0x00   (C34F)
X ≥ 0xE6              → ушёл ВЛЕВО:   сосед +2, X := 0xA8   (C346)
X < 0xA9 и Y < 0x20   → ушёл ВВЕРХ:   сосед +0, Y := 0x60   (C365)
X < 0xA9 и Y ≥ 0x61   → ушёл ВНИЗ:    сосед +1, Y := 0x20   (C35D)
иначе                 → перехода нет  (C35C ret c)
```

(`X ≥ 0xE6` — это «X ушёл ниже нуля и завернулся».) Ровно та же четвёрка и в
том же порядке разбирается у бродячих персонажей (`C105`..`C127`), там индекс
соседа кладётся в `e` = 0,1,2,3 и читается как `hl + e` после `D16C` — это
независимое подтверждение.

### 2.3 Карта: мир — прямоугольная сетка 5 × 18

Замер по всем 87 записям (скрипт разбора — `tools/marker/extract.py`, данные —
`build/marker/data.json`, поле `rooms[].nb`): соседи почти везде задаются
**арифметикой**

```
вверх = i − 5     вниз = i + 5     влево = i − 1     вправо = i + 1
(0 = «выхода нет»)
```

Отклонений от формулы **ровно 12 байт из 348**:

| комната | сторона | по формуле | на самом деле |
|---|---|---|---|
| `18` | вправо | `19` | **`28`** |
| `28` | влево | `27` | **`18`** |
| `1D` | вправо | `1E` | **`2B`** |
| `2B` | влево | `2A` | **`1D`** |
| `2A` | вправо | `2B` | **`38`** |
| `38` | влево | `37` | **`2A`** |
| `2D` | вправо | `2E` | **`3D`** |
| `3D` | влево | `3C` | **`2D`** |
| `52` | вниз | `57` (нет такой) | **`56`** |
| `56` | все четыре | — | **`0` (выходов нет)** |

Первые восемь — четыре **взаимных** нештатных перехода `18⇄28`, `1D⇄2B`,
`2A⇄38`, `2D⇄3D`: это «мосты» между удалёнными частями замка (мануальное «два
замка, соединённые между собой»). Остальное — тёмная комната `56`, см. § 7.3.

Побочный эффект «мостов» — **шесть односторонних проходов**: соседи
переставленных комнат свои формульные значения сохранили, а сами
переставленные — нет. Например из `19` влево попадаешь в `18`, а из `18`
вправо — уже не в `19`, а в `28`. Полный список «туда можно, обратно
нельзя»:

```
18 ↛ 19     1D ↛ 1E     28 ↛ 27     2D ↛ 2E     38 ↛ 37     3D ↛ 3C
```

Проверка симметрии по всем 348 байтам даёт ровно **22** несимметричные
связи, и все 22 объясняются этими шестью, четырьмя «мостами», нулями на
краях карты и комнатой `56`. Никаких других сюрпризов в таблице нет.

**Карта: `build/manual/map.png`** — сетка 5 × 18 со всеми пометками (комнаты
предметов, двери, враги, нештатные переходы, закрытые стороны).

Текстом та же карта (строка = ряд сетки, слева направо — колонки 0..4):

```
     кол0 кол1 кол2 кол3 кол4
ряд 0:  00   01   02   03   04
ряд 1:  05   06   07   08   09
ряд 2:  0A   0B   0C   0D   0E
ряд 3:  0F   10   11   12   13
ряд 4:  14   15   16   17   18 → 28
ряд 5:  19   1A   1B   1C   1D → 2B
ряд 6:  1E   1F   20   21   22
ряд 7:  23   24   25   26   27
ряд 8:  28   29   2A   2B   2C        28←18, 2A→38, 2B←1D
ряд 9:  2D   2E   2F   30   31        2D→3D
ряд10:  32   33   34   35   36
ряд11:  37   38   39   3A   3B        38←2A
ряд12:  3C   3D   3E   3F   40        3D←2D
ряд13:  41   42   43   44   45
ряд14:  46   47   48   49   4A
ряд15:  4B   4C   4D   4E   4F
ряд16:  50   51   52   53   54        51 ↓ 56,  52 ↓ 56
ряд17:  55                            55 → 56;  56 — тёмная, вне сетки
```

Края: у комнаты `00` нет выходов вверх и влево (единственная, где закрытая
сторона задана явным нулём). У `53`, `54`, `55` «вниз» ведёт в записи
`58`/`59`/`5A`, которых **не существует** (таблица кончается на `56`):
`D16C` в этом случае уйдёт за конец таблицы в банк цвета. В обычной игре
это не срабатывает — **предположение**: нижний край этих комнат закрыт
полом. Но переход НЕ ЗАКРЫТ КОДОМ: замер 2026-09-23 —
`tools/cmp_allrooms_msx.py` роняла героя в эти комнаты по воздуху, и он
спокойно уходил вниз в `58`, `59`, `5A`; игра не срывалась, а продолжала
рисовать «комнаты» из банка цвета, с соседями вроде `5F BF BF 80`. То есть
защита тут одна — геометрия пола, и проверять её надо на живом проходе, а
не на стенде, который героя роняет.

Отдельная особенность формулы: «вправо» из колонки 4 даёт `i+1`, то есть
колонку 0 **следующего** ряда, и наоборот. Замка это не рвёт (карта связна),
но геометрически выглядит как «заворот строки». Закрыты ли эти переходы
стенами в самих комнатах — **не проверено**.

## 3. Герой («гномик» — на самом деле МАГ)

Программный движок героя — `D690..DAC9` в резидентном слое, логика — `C160`,
параметры кадра — `C245` (`docs/render-paths.md` § B).

### 3.1 Переменные

`GAME_VARS = C1EA`, 21 байт. Что важно игроку:

| адрес | смещение | смысл | где доказано |
|---|---|---|---|
| `C1EA` | `+0` | флаг «контрольная точка уже сохранена» | `C21F`, `C38C` |
| `C1EB` | `+1` | горизонтальный импульс в прыжке | `C441`, `C433` |
| `C1ED` | `+3` | накопленная высота падения | `C3F2`, `C1C1` |
| `C1EE` | `+4` | «идёт» (нажата влево/вправо) | `C1A8`, `C1B7` |
| `C1EF` | `+5` | фаза выстрела 1..5 | `C3A8` |
| `C1F0` | `+6` | фаза прыжка 1..7 | `C425`, `C441` |
| `C1F1` | `+7` | номер кадра образа героя | везде |
| `C1F2` | `+8` | **ЖИЗНИ** | `C212 ld hl,0x0103` |
| `C1F4` | `+0xA` | **Y** | `C245`, `D868` |
| `C1F5` | `+0xB` | **X** | там же |
| `C1F6` | `+0xC` | **номер верхней (игровой) комнаты** | `C349`, `C64A` |
| `C1F7` | `+0xD` | «стоит на лестнице» | `C4BB`, `C240` |
| `C1F8` | `+0xE` | поворот: `0` влево, `0x80` вправо | `C1E1`, `C318` |
| `C1FA..C1FE` | `+0x10..+0x14` | **контрольная точка** (Y, X, комната, лестница, поворот) | `C21F`, `BBB1` |

Старт новой игры — `C1FF`: всё обнуляется, затем `X = 0x40`, `Y = 0x50`
(`C20C ld hl,0x4050`), **жизней 3** (`C212 ld hl,0x0103`), поворот `0x80`
(вправо). Номер комнаты остаётся нулём — **герой всегда начинает в комнате
`00`**, в левом верхнем углу карты.

### 3.2 Что умеет

Опрос управления — `CC7B` → `CC87` (пять клавиш через `KBD_SCAN`, таблица
`CC95`); ответ собирается в `b`, биты: `0` вверх, `1` вниз, `2` влево,
`3` вправо, `4` огонь. Разбор — `C196`..`C1BB`.

| действие | клавиша | код | что делает |
|---|---|---|---|
| **идти влево/вправо** | `O` / `P` | `C274` / `C25D` | первое нажатие в новую сторону только **разворачивает** героя (`C1E1`, `xor 0x80`); дальше шаг **3 пикселя** за кадр (`C318`: `b = 0xFD` или `+3`) |
| **прыжок** | `Q` | `C441` → `C425` | 7 кадров вверх по **4 пикселя** (`C2A7`, `b = 0xFC`), итого ≈ 28 px; в прыжке по горизонтали **2 пикселя** за кадр (`C320`) и только если перед прыжком герой шёл (`C449`: `GAME_VARS+4` в 1..4 → `+1 := 1`) |
| **присесть** | `A` | `C27C` → `ld a,5 / ld (GAME_VARS+7),a` | кадр 5; в этом положении **коробка столкновений ниже** (`C8FB`: при кадре 5 `d := 0x14`) — под низко летящим можно пролезть |
| **лестница** | `Q` / `A` на лестнице | `C290` / `C287` | ±4 пикселя за кадр (`C2A3`/`C2A7`) |
| **молния** | ПРОБЕЛ | `C39F` → `C3A8` | см. § 3.3 |
| **взять предмет** | SHIFT (на Векторе `СС`) | `C9B5`, опрос в `C9BA` | см. § 4.3 |
| **пауза** | `H` | `D684` (`KBD_CHK`), `CC5D` | строка 3 бит 5 |
| **смотреть в нижнем окне** | `1`..`5` | `BF83`, опрос в `BF8E` | см. § 5.3 |

Лестница определяется не клавишей, а полом под ногами: `C4BB` берёт три
знакоместа на высоте `Y − 0x1C` (X+6, X+12, X+18) из **теневого буфера
атрибутов** `F34D` и проверяет бит `0x20`. Если во всех трёх он есть —
`GAME_VARS+0xD := 0x0A`, кадр 0x0A, герой «на лестнице».

Классы атрибута (`D4B8`, `D4CF`): `0x00` — фон, `0x20` — **лестница**,
`0x40` — «твёрдо только в воздухе», `0x80` — **твёрдый пол/стена**.
Ходьба упирается в `≥ 0x80` (`C269 ld d,0x80`), а прыжок и падение — уже в
`≥ 0x40` (`C40C`, `C438`). То есть **есть поверхности, сквозь которые можно
пройти пешком, но нельзя пролететь в прыжке**.

### 3.3 «Точность прыжков» — как это устроено на самом деле

Жалоба с форума (zx-pk.ru) на «точность прыжков» объясняется тремя вещами,
все видны в коде:

1. **Горизонтальная скорость в прыжке вдвое меньше, чем при ходьбе**:
   3 px/кадр пешком (`C318`) против 2 px/кадр в прыжке (`C320`). Прыжок
   «не долетает» ровно настолько.
2. **Импульс решается в момент отрыва и больше не меняется**: `C441`
   смотрит `GAME_VARS+4` («шёл ли герой») и ставит `GAME_VARS+1` = 0 или 1
   один раз. Нажать «вперёд» уже в воздухе бесполезно — `C425`/`C3EF`
   читают только `+1`.
3. **Приземление проверяется тремя точками с шагом 6 пикселей** (`C2BA` →
   `C2D6`: `e = 3`, каждый заход `b := X + 6`). Пола хватает уже под одной
   из трёх — но все три лежат в полосе **X+6 … X+18**, то есть под
   «серединой» героя шириной 24 px. Край площадки шириной меньше 6 px герой
   просто не замечает.

Потолок в прыжке проверяется одной пробой на `Y − 0x21` (`C2C8`: `a = 0xDF`,
`d = 0x80`) — с низким потолком прыжок обрывается.

### 3.3a «Двойной прыжок с платформы» — так и в оригинале

Подробный разбор с числами и сверкой с живым картриджем —
`docs/jump-geometry.md`. Коротко:

* **высота прыжка 24 px, а не 28.** Подъёмов шесть (`C425`, фазы 2..7, по
  4 px): фаза 1 (`C441`) `Y` не меняет, на фазе 7 прыжок кончается
  (`C461`). Старт `Y = 0x50` → апогей `Y = 0x38`, замерено на обеих
  машинах;
* **прыгнуть в воздухе нельзя.** В падении `C16F` делает `jp C3EF` и
  возвращается в `C245` **мимо опроса клавиш**; в прыжке `C18C` уводит на
  `C425` — тоже мимо. Ни `Q`, ни джойстик в полёте игра не видит;
* **но прыжок ПРОДОЛЖАЕТСЯ в комнате сверху.** Как только в прыжке
  `Y < 0x20`, `C32C` меняет комнату и ставит `Y := 0x60` (низ нового
  экрана), а фаза прыжка и `GAME_VARS+9 = 0` сохраняются — оставшиеся
  фазы поднимают героя уже там. Это и выглядит «двойным прыжком»;
* **с зажатой `Q` следующий прыжок начинается в тот же виток, когда герой
  приземлился** — после посадки ввод опрашивается сразу.

Оба эффекта воспроизведены одинаковым вводом по итерациям на живом MSX
(`ref/msx/rom/*[4397].rom`) и на нашем образе i8080: `GAME_VARS` совпали
**2045 из 2045 итераций, 0 расхождений** (`tools/jump_msx_cmp.py`).

Практический вывод для игрока: **подняться этажом выше можно только с
уступа** (нужна опора не ниже `Y = 0x34`) **или по лестнице**. С ровного
пола (`Y = 0x50`) апогей `0x38` до порога `0x20` не достаёт никогда.

### 3.4 Молния (`rayo`) — чем стреляет и по кому

Выстрел — `C39F`:

```
C39F  ld a,(BF09) / or a / ret nz      ; молния уже в полёте — нельзя
      call C240 / ret nz               ; на лестнице — нельзя
C3A8  фаза += 1 (GAME_VARS+5), кадр героя 8 или 9
      фаза 2 → создать снаряд:
        (BF09+0) := 2                  ; «живой»
        (BF09+6) := 0x1C               ; образ 0x1C — вспышка молнии
        (BF09+1) := номер комнаты
        (BF09+7) := поворот героя
        (BF09+4/+5) := Y−10, X−8 (влево) или X+16 (вправо)
      фаза 5 → сброс (C3E8)
```

Образы молнии — `0x1B`, `0x1C`, `0x1D` (13 строк × 16 px) из банка `E04B`,
перебираются в `BE1A`/`BE1C`.

**Выстрел стоит 1 деление энергии**: `BE1C` при переходе снаряда в состояние 1
делает `ld (iy+0),1 / jp C92C` (`BE33`), а `C92C` — это и есть «убавить
энергию на единицу».

**Что молния делает с врагами — `BD42`:**

```
BD42  ld a,(BF09) / cp 1 / ret nz        ; снаряд должен лететь
      коробка: X снаряда −0x18…+8, Y снаряда −8…+0x28
      ld a,(iy+4) / add a,0x32 / ld (iy+4),a   ; ← +50 к счётчику задержки
      затем снаряд гасится (BDDD)
```

`iy+4` — это счётчик «спит N кадров» в записи врага (`C86A`: пока он не ноль,
враг не двигается и **не бьёт героя**, см. § 7.1). То есть **молния не
убивает, а оглушает примерно на 50 кадров** и сама при этом исчезает.

Единственная цель, которую молния уничтожает, — **орёл** (`C0AF`, § 5.4).

### 3.5 Энергия и жизни

* **Жизни — три** (`C212 ld hl,0x0103` → `GAME_VARS+8 = 3`). В панели три
  фигурки, ряды 1..4, знакоместа 25..30 (`docs/render-paths.md` § C.4).
  Потеря — `CA7B`: звук, `dec (GAME_VARS+8)`, затем `CDD8` гасит очередную
  фигурку (цвет `0xA0` вместо `0xF1`).
* **Энергия — 47 делений** в 6 знакоместах полоски ENERGIA (ряд 8, колонки
  25..30). Заливка и сброс счётчика — `CA0C` (`ld a,0x2F / ld (C92D),a`);
  счётчик живёт как самомодифицируемый операнд по `C92D`.
* **Убавить на единицу — `C92C`.** При нуле: `ld a,0x02 / jp C627` — смерть.
* Полоска восстанавливается полностью: при старте уровня (`CA49`), **после
  потери жизни** (`BBAE`) и **после подбора предмета** (`CAD2`).

**Откуда теряется энергия (исчерпывающе, по всем вызовам `C92C`/`C926`):**

| сколько | за что | адрес |
|---|---|---|
| −1 за кадр касания | любой из 20 патрульных врагов | `C805` (`ld a,0x1E / call C926`) |
| −1 за кадр касания | стрела демона-лучника | `BE36` (`ld a,0x03`) |
| −1 за кадр касания | набегающий оборотень | `BE63` (`ld a,0x0E`) |
| −1 за кадр в огне | пламя (образ `0x24`/`0x25`) | `BCE1` → `BCF3` |
| −1 | собственный выстрел | `BE33` |
| − (высота − 15) | падение с высоты больше 16 px | `C1BE`..`C1DC` |
| **вся сразу** | тёмная комната `56` | `C60D` → `C61E`/`C622` |

Падение: `C3EF` наращивает `GAME_VARS+3` на каждый кадр полёта; при
приземлении `C1BE` смотрит: если меньше `0x10` — бесплатно, иначе
`b = высота − 0x0F`, обрезанное текущей энергией, и столько раз зовётся
`C92C`.

### 3.6 Смерть и рестарт — что теряется

Смерть = `C625` (`ld a,1`) или `C627` с `a=2` из `C92C`; оба пишут в
самомодифицируемый байт `BF38`. Дальше `BBA5`:

```
BBA5  call CA7B                          ; −1 жизнь, погасить фигурку
      если жизней 0 → BBCC (экран итога)
      call CA0C                          ; энергия снова 47
      ldir GAME_VARS+0x10..+0x14 → +0xA..+0xE   ; ВЕРНУТЬ контрольную точку
      call C38C                          ; перерисовать комнату
      call C464 / C1DC                   ; сбросить прыжок и счётчик падения
```

**Контрольная точка — место, где герой ВОШЁЛ в текущую комнату.** Сохраняет
её `C21F`, и только один раз на комнату: флаг `GAME_VARS+0` ставится при
сохранении и снимается при каждой перерисовке комнаты (`C38C`; на смене
комнаты туда приходит `D619` → `jp C38C`, `D630`).

**Что НЕ теряется при смерти:** взятые предметы (`LEVEL_VARS+7/+9/+B`),
расколдованные персонажи, открытые двери, карта посещённых комнат, счётчик
процентов. Теряется только жизнь и вся энергия.

**Что теряется при потере последней жизни:** всё. `CA3D` при новой игре
зовёт `C1FF` (жизни, позиция, комната `00`), `CE6A` (сброс всех рычагов и
новый розыгрыш мест предметов), очистку `F2B9` и `CD42` (`CA58`..`CA66`).

## 4. Предметы: три слота, 18 мест, три из них на игру

### 4.1 Что за предметы

Слоты — `LEVEL_VARS = CD7B`, 13 байт:

| байт | смысл |
|---|---|
| `CD7B` (`+0`) | номер комнаты **нижнего окна** |
| `CD7C`/`CD7D` (`+1`/`+2`) | слот 0: комната и X |
| `CD7E`/`CD7F` (`+3`/`+4`) | слот 1: комната и X |
| `CD80`/`CD81` (`+5`/`+6`) | слот 2: комната и X |
| `CD82` (`+7`) | слот 0 взят |
| `CD84` (`+9`) | слот 1 взят |
| `CD86` (`+0xB`) | слот 2 взят |

Обработчики берутся из `JUMP_TABLE_CD88` (`iy+0x0C`/`+0x0D` для рисования,
`iy+0x12`/`+0x13` для показа значка):

| слот | образ в комнате | что нарисовано (банк `E04B`, отрисовано из данных) | подставка | значок панели | цвет значка |
|---|---|---|---|---|---|
| **0** | `0x18`, 16×16 | **ШАР** — сплошной круг | `0x16` (`CD5A`) | `CD12`, ряд 16 кол. 25, 3×3 | `0xF1` белый |
| **1** | `0x17`, 24×32 | **РАСКРЫТАЯ КНИГА** | `0x16` (`CD56`) | `CD1F`, ряд 12 кол. 25, 3×4 | `0xA0` тёмно-жёлтый |
| **2** | `0x19`, 24×8 | **ЖЕЗЛ** — тонкий стержень со звездой наверху | нет (`CD4D`) | `CD2C`, ряд 12 кол. 29, 3×2 | `0x50` голубой |

Цвет спрайта берётся из `F317 + номер образа` (`SPIRITS.1[0x238F]`):
шар — `0x0F` белый, книга — `0x0A` тёмно-жёлтый, жезл — `0x07` циан,
подставка — `0x0C` тёмно-зелёный.

Подставка `0x16` — «тумба» с ножками, рисуется на своём месте **и после
подбора, каждый кадр** (`CD5C` → `CD70`), подробности —
`docs/adapter-requirements.md` § 0e.

### 4.2 Где появляются — розыгрыш `CE6A`

```
CE6A  11 адресов из CECE..CEE3 := 0x36      ; снять бит «рычаг сработал»
      9 троек с CEE4                         ; вернуть счётчики элементов дверей
      8 байт CEFE..CF05 → 0x7F9C             ; читателей нет
CE8B  ld a,r / and 0x0F / inc a              ; ← СЛУЧАЙНОЕ ЧИСЛО 1..16
CE90  hl = PARAM_TABLE_CEAA; шагнуть (a−1) раз по 2 байта
CE9A  ldir 6 байт → LEVEL_VARS+1..+6          ; ТРИ пары «комната, X»
CEA2  6 нулей → LEVEL_VARS+7..+0xC            ; флаги «не взят»
```

То есть из таблицы `PARAM_TABLE_CEAA` (`CEAA..CECD`, **18 пар** «комната, X»)
берётся **окно из трёх подряд идущих пар**, начиная с пары 0..15. Значит
разных раскладов **16**, комнат-кандидатов **18**:

| # | комната | X | # | комната | X |
|---:|---:|---:|---:|---:|---:|
| 1 | `09` | `78` | 10 | `3C` | `90` |
| 2 | `35` | `90` | 11 | `27` | `58` |
| 3 | `1C` | `80` | 12 | `48` | `50` |
| 4 | `0F` | `50` | 13 | `50` | `28` |
| 5 | `44` | `20` | 14 | `2E` | `50` |
| 6 | `12` | `88` | 15 | `1E` | `98` |
| 7 | `4D` | `24` | 16 | `45` | `04` |
| 8 | `23` | `3C` | 17 | `1A` | `98` |
| 9 | `43` | `60` | 18 | `53` | `90` |

Y подставки зашит намертво: низ образа `0x50` (`CD73 ld a,0x50`), в нижнем
окне `+0x60`.

Сразу после розыгрыша `CA69` делает `ld a,(LEVEL_VARS+1) / ld (LEVEL_VARS),a`
— **нижнее окно с самого начала показывает комнату, где лежит ШАР**. Это и
есть «подсказка», обещанная инструкцией.

### 4.3 Как подобрать — `C9B5` (`12B5`)

```
C9B5  ld a,(iy+6) / or a / ret nz          ; уже взят
C9BA  ld a,0xF6 / out (AA) / in (A9) / bit 0,a / ret nz
                                           ; ← строка 6 бит 0 = SHIFT (на Векторе «СС»)
C9C6  проверка, что X героя попал в окно [X предмета − 4 … X предмета + 4)
C9D4  ld (iy+6),1                          ; пометить «взят»
C9D9  hl = (iy+0x12),(iy+0x13) / jp (hl)   ; CD12 / CD1F / CD2C — показать значок
```

Обработчик значка (`CD12`/`CD1F`/`CD2C`) красит прямоугольник в панели и,
общим хвостом `CD34`..`CD3F`, прибавляет `0x0F` к `CD42` (проценты).
Звуковой/визуальный «плюсик» очков рисует `C079`-независимый путь `CAA0`
для расколдовываний; после подбора предмета энергия восстанавливается
полностью (`CAD2 jp CA0C`).

**Клавиша «действие у объекта»** из `docs/v06-input-sound.md` (векторный
адрес `12BC`) — это ровно `C9BC` MSX, то есть **подбор предмета и ничего
больше**. Другой «функции SHIFT» в игре нет.

### 4.4 Первый шаг: пока нет шара, книги и жезла НЕТ в комнатах

`C975` (зовётся каждый кадр из `BF55`):

```
C975  ld iy,LEVEL_VARS+1
      ld b,0x03
      ld a,(LEVEL_VARS+7) / or a / jr nz,C983
      ld b,0x01                 ; ← ШАР НЕ ВЗЯТ: цикл только по ОДНОМУ слоту
```

То есть **книга и жезл не рисуются и не подбираются, пока не взят шар**.
Инструкция об этом молчит, а игрок без этого знания ищет книгу зря.

## 5. Персонажи истории и как закончить игру

### 5.1 Три «крупных объекта» — `OBJ_ARRAY_CBBF`

3 записи по 13 байт (`CBBF`, начальные значения копируются из `OBJ_ARRAY_INIT
= CBE6` процедурой `CA8D`). Поля: `+3` базовый образ, `+6` комната,
`+7` Y, `+8` X, `+9` состояние, `+0xA` «особый» образ, `+0xB` текущий образ.

| запись | база | образы | кто это | стартовая комната | клавиша |
|---|---|---|---|---|---|
| 0 (`CBBF`) | `0x27` | `0x27`–`0x29` + `0x2A` | **ДОСПЕХ** (фигура в шлеме со щитом, циан) | `0x0B` | `4` |
| 1 (`CBCC`) | `0x2B` | `0x2B`–`0x2D` + `0x2E` | **ПРИНЦЕССА** в заколдованном виде (карлик в колпаке, белый) | `0x32` | `3` |
| 2 (`CBD9`) | `0x2F` | `0x2F`–`0x31` + `0x32` | **ОРЁЛ** (птица в полёте, тёмно-жёлтый) | `0x53` | `5` |

Соответствие «запись ↔ клавиша» доказано адресами в `BF83`: клавиша `3`
читает `CBBF+0x16` и `+0x13` (это запись 1), клавиша `4` — `+0x9` и `+0x6`
(запись 0), клавиша `5` — `+0x20` (запись 2).

Все трое **бродят по замку сами**, пользуясь той же четвёркой соседей
(`C0E8` → `C14D call D16C` → `add hl,de`, `de` = 0..3).

### 5.2 Расколдовывание — `C079`

Столкновение героя с персонажем даёт `e ≠ 0` из `C8F2`, и тогда зовётся
`C079` с `b` = номером итерации цикла `C001` (`b = 3` для записи 0,
`b = 2` для записи 1, `b = 1` для записи 2):

```
C079  ld a,(iy+9) / or a / ret nz          ; персонаж уже не в исходном виде
      cp 0x03 / jr z,C09B                  ; ДОСПЕХ
      cp 0x02 / jp nz,C625                 ; ← ОРЁЛ: СМЕРТЬ
      ; ПРИНЦЕССА:
      ld a,(LEVEL_VARS+0xB) / or a / ret z ; ЖЕЗЛ не взят → ничего
      ld a,5 / ld (CBBF+0x16),a            ; состояние 5
      ...
C09B  ; ДОСПЕХ:
      ld a,(LEVEL_VARS+9) / or a / ret z   ; КНИГА не взята → ничего
      ld a,2 / ld (CBBF+0x9),a             ; состояние 2
```

* `LEVEL_VARS+9` — флаг слота **1 = книга** → расколдовывает **доспех**;
* `LEVEL_VARS+0xB` — флаг слота **2 = жезл** → расколдовывает **принцессу**.

Ровно как обещает инструкция («la vara de poder para desencantar a la
princesa, el libro sagrado para desencantar a la armadura hechizada»).

Состояние ведёт `C062`: пока оно ≥ 4, каждый кадр `dec (iy+9)`, а образ
берётся из таблицы `C0E2 + состояние` (`C0E4..C0E7` = `27 34 32 33`). Значит
принцесса (состояние 5) проходит **анимацию превращения**: образ `0x33`
(рябь) → `0x32` → и навсегда `0x34` — **девушка в платье**. Доспех
(состояние 2) сразу встаёт на образ `0x27`.

Расколдованный персонаж перестаёт быть опасным: `C001` пропускает запись при
`(iy+9) == 1`, а `C039`..`C044` доводит состояние до 1, когда персонаж
уходит из видимых комнат.

### 5.3 Нижнее окно и клавиши `1`..`5` — `BF83`

```
BF83  ld a,(LEVEL_VARS+7) / or a / ret z   ; ← БЕЗ ШАРА НЕ РАБОТАЕТ ВООБЩЕ
BF8C  ld a,0xF0 / out (AA) / in (A9) / and 0x3E    ; строка 0, биты 1..5 = клавиши 1..5
      0x3C (кл.1) → BFD0 : если слот 1 не взят — показать комнату LEVEL_VARS+3 (КНИГА)
      0x3A (кл.2) → BFDA : если слот 2 не взят — показать комнату LEVEL_VARS+5 (ЖЕЗЛ)
      0x36 (кл.3) → BFC6 : если (CBBF+0x16) ≠ 1 — показать комнату записи 1 (ПРИНЦЕССА)
      0x2E (кл.4) → BFBC : если (CBBF+0x9)  ≠ 1 — показать комнату записи 0 (ДОСПЕХ)
      0x1E (кл.5) → BFB7 : показать комнату записи 2 (ОРЁЛ), без условий
BFE4  ld (LEVEL_VARS),a  → jp CA72 (перерисовать нижнее окно)
```

Заметь: клавиши `1` и `2` перестают работать, **когда предмет уже взят**
(`BFD0`: `or a / ret nz`) — показывать больше нечего. Клавиши `3` и `4`
перестают работать, когда персонаж доведён до состояния 1.

Клавиша отпущена — `BF99`/`BFEE` возвращают прежнее окно; то есть держать
клавишу надо, пока смотришь.

### 5.4 Конец игры — убить орла (`C0AF`)

```
C0AF  cp 0x01 / ret nz                     ; только для записи 2 (ОРЁЛ)
      ld a,(BF09) / cp 1 / ret nz          ; молния должна быть в полёте
      ld a,(CBBF+0x16) / or a / ret z      ; ПРИНЦЕССА ещё не расколдована → нельзя
      ld a,(CBBF+0x9)  / or a / ret z      ; ДОСПЕХ ещё не расколдован  → нельзя
      коробка молнии (X −0x18…+8, Y −8…+0x28) против орла
      ld a,0x01 / ld (BBD4),a              ; ← ПОБЕДА
```

`BBD4` проверяется в главном цикле (`BB92`) и уводит на `BCF6`: герой встаёт
в победную позу (образы `0x0C` и `0x0B`), играет финальная музыка, ждёт
клавишу — и **начинается новая игра** (`jp BB89`).

**Порядок обязателен: шар → книга и жезл → доспех и принцесса → орёл.**

## 6. Двери и рычаги

Диспетчер — `C4E3`, зовётся каждый кадр (`BF80 jp C4E3`). По номеру верхней
комнаты уходит на обработчик; всего восемь комнат с рычагами плюс комната
`56` (тёмная).

**Рычаг — элемент комнаты с образом `0x36`** (в банке декораций это
диагональная ручка 8×16). Проверка `C65D`:

```
C65D  ld a,(hl) / and 0x80 / jr z / scf / ret   ; бит 7 = «уже сработал»
C664  X героя должен попасть в [X рычага − 8, X рычага + 6]
      Y героя должен попасть в [Y рычага − 0x22, Y рычага − 0x1C]
C680  ld (hl),0xB6                              ; образ 0x36 → 0xB6 (бит 7)
```

Никакой клавиши не нужно — **достаточно встать вплотную к рычагу на нужной
высоте**. После срабатывания рычаг рисуется незеркалённым, то есть визуально
«переключается».

Открытие двери сделано хитро: обработчик пишет **меньшее** число в байт `+5`
заголовка какой-то комнаты, и `D184` перестаёт рисовать последние N элементов
её списка — створки исчезают (`docs/render-paths.md` § C.1):

| рычаг в комнате | адрес рычага | какая комната открывается | было→стало | что исчезает |
|---|---|---|---|---|
| `50` | `A54C` | `50` (та же) | 32→30 | 2 × образ `0x15` (решётка) |
| `04` | `8648` | `04` (та же) | 35→33 | 2 × `0x15` |
| `0D` | `89DE` | **`13`** | 42→40 | 2 × `0x05` |
| `18` | `8EAC` | `18` (та же) | 36→30 | 4 × `0x01` + 2 × `0x37` |
| `1F` | `91AE` | **`1E`** | 35→29 | 4 × `0x01` + 2 × `0x37` |
| `3D` | `9D7A` | **`3F` и `40`** | 24→18, 26→20 | 5 × `0x2A` + `0x2B` в каждой |
| `4A` | `A27C` | `4A` (та же) | 21→20 | 1 × `0x32` |
| `4C` | `A360` | `4C` (та же) | 35→34 | 1 × `0xB2` |

**Три рычага открывают проход в ДРУГОЙ комнате** — `0D` открывает `13`,
`1F` открывает `1E`, `3D` открывает сразу `3F` и `40`. Это отдельный источник
«непонятно, что произошло»: дёрнул рычаг, а на экране ничего не изменилось.
Игра это даже учитывает: `C570`..`C575` проигрывает анимацию створки, только
если в нижнем окне как раз показана комната `1E`.

**Кто из восьми рычагов вообще зовёт прямой вывод** (замер
`tools/cmp_lever_msx.py`, 2026-09-23; у комнат `4A` и `4C` рычагов в
записи по нескольку, и «лишние» как раз и включают анимацию):

| рычаг | что зовёт обработчик | условие |
|---|---|---|
| `04`, `18`, `50` | `C6A7` — полоса уезжает | нет |
| `4A` (элемент `A280`), `4C` (`A364`) | `C719` — створка ползёт вбок | нет |
| `4A` (`A27C`), `4C` (`A360`) | `8374` — створка двери | нет |
| `1F` | `C6A7` | **только если `LEVEL_VARS+0 == 0x1E`** |
| `0D`, `3D` | ничего, только звук | — |

То есть «эффектов ноль» в обычном прогоне — законный исход, а не дыра:
рычаг надо сперва дёрнуть, а у трёх рычагов из восьми анимации нет либо
она условная.

Все рычаги сбрасываются в исходное состояние при старте новой игры
(`CE6A`: 11 адресов `CECE..CEE3` получают `0x36`, 9 троек с `CEE4`
возвращают счётчики элементов).

**Ловушек, которые включаются рычагом** («activan trampas» из инструкции),
в разобранном коде **не найдено** — все восемь обработчиков только убирают
элементы. **Предположение:** инструкция описывает и то, что в игру не попало.

## 7. Враги и ловушки

### 7.1 Двадцать патрульных — `OBJ_TABLE_B6A2`

20 записей по 9 байт, обход — `C7DB` (`ld b,0x14` = 20). Поля: `+0` Y,
`+1` X, `+2` комната, `+3` образ, `+4` счётчик/направление (бит 7),
`+5`/`+6` предел А (комната, X), `+7`/`+8` предел Б.

Кто это (образы из банка `E04B`, цвет из `F317`):

| образы | кто | цвет | сколько |
|---|---|---|---|
| `0x13`–`0x15` | **призрак** в балахоне | `0x0F` белый | 10 |
| `0x10`–`0x12` | **горбун** с копьём | `0x07` циан | 6 |
| `0x0D`–`0x0F` | **оборотень** | `0x0A` тёмно-жёлтый | 4 |

Движение — `C875`..`C8F1`: шаг **3 пикселя** по X, при достижении предела
направление переворачивается (`C8A3`: `xor 0x80`). Выйдя за X ≥ 0xA3 или
≥ 0xE6, враг переходит в **соседнюю по НОМЕРУ комнату** (`inc (iy+2)` /
`dec (iy+2)`), а не по таблице соседей. То есть патруль идёт по «ряду»
сетки.

Касание — `C805`: `ld a,0x1E / call C926` → −1 деление энергии за кадр.
Важно: проверка идёт только в кадры, когда счётчик задержки `(iy+4)` равен
нулю (`C7ED`..`C7F2`), то есть **оглушённый молнией враг 50 кадров не
кусается** — это и есть польза от стрельбы.

**Убить патрульного нельзя.** Единственное, что с ним делает молния, —
`BD42`, `+0x32` к счётчику задержки.

### 7.2 Случайные гости — `OBJ_BLOCK_BF09`

4 записи по 11 байт, `BF09`, `BF14`, `BF1F`, `BF2A`:

| запись | образы | кто | урон |
|---|---|---|---|
| 0 (`BF09`) | `0x1B`–`0x1D` | **молния героя** | своя энергия −1 (`BE33`) |
| 1 (`BF14`) | `0x26` | **стрела** (её пускает лучник) | −1 за кадр (`BE36`) |
| 2 (`BF1F`) | `0x1F`–`0x21` | **набегающий зверь** (собака/волк, пурпурный) | −1 за кадр (`BE63`) |
| 3 (`BF2A`) | `0x22`, `0x23` | **демон-лучник** (32×32, белый) | сам не бьёт, стреляет |

Появление — `BEB7` (из `BD9B`, каждый кадр): если ни зверь, ни лучник не
заняты, `BE8D` тянет `ld a,r`, и только при `(a and 0x3F) < 3` (≈ 3 шанса
из 64 на кадр) появляется **либо зверь, либо лучник** (`and 0x01` в `BEC7`),
с той стороны экрана, которая дальше от героя (`BE92`..`BEA0`: порог
X = `0x54`). Лучник на 4-й фазе (`BE44 → BE68`) запускает стрелу.

То есть враги приходят **в любую комнату, где стоишь**, а не только в «свои».

### 7.3 Тёмная комната `56` — задумано так, это не баг

`C4E3` → `C505 cp 0x56 / jp z,C60D`:

```
C60D  hl=0x6360 bc=0x0205 a=0xF1 / call CF28   ; проявить белым 2 ряда × 5 знакомест
      call CAD5                                ; ДВАЖДЫ мигнуть картинкой
      ld a,(C92D) / ld b,a / call C1D5         ; ← b = ВСЯ оставшаяся энергия,
                                               ;   b раз C92C → энергия в ноль
```

`CAD5`/`CAE8` копируют по `0x28` байт из `GFX_B540` и `GFX_B540+0x50` в
знакоместа ряда 3, колонок 12..16, с длинной паузой между показами — это и
есть «существо с огромными глазами», мигающее в темноте.

Сама комната почти пуста: её запись (`A782`) содержит **5 одинаковых
элементов** — образ `0x0D` в столбик по `X = 0x40`, `Y = 00, 08, 10, 18, 20`
(тёмно-жёлтые чернила), то есть свисающая сверху цепь, по которой герой туда
и падает. Всё остальное в комнате — чернота.

Комната `56` — **единственная в игре без выходов** (все четыре соседа = 0).
Входов в неё, наоборот, три (сплошной поиск по всем 87 записям):

| откуда | как |
|---|---|
| `51` | вниз (`51 + 5 = 56`, обычная формула) |
| `52` | вниз (нештатный переход: по формуле было бы `57`, которой нет) |
| `55` | вправо (`55 + 1 = 56`, обычная формула) |

Выйти нельзя, энергия снимается вся → `C92C` при нуле делает
`ld a,0x02 / jp C627`, то есть смерть.

Куда возвращает: контрольная точка (`GAME_VARS+0x10..0x14`) была сохранена
`C21F` **до** перехода — внутри кадра `C21F` вызывается из `C160` (`C193`), а
смена комнаты происходит позже, в `C245 → C32C`, и `C4E3` (а с ним `C60D`)
отрабатывает уже после. Пока герой мёртв, `BF37` уводит в обход `C160`, и
`C21F` в комнате `56` не срабатывает ни разу. Поэтому в контрольной точке
остаётся положение в **той комнате, откуда герой пришёл**, и после гибели он
оказывается там же (в двух случаях из трёх — **на экран выше**), с −1 жизнью
и полной энергией. Ровно то, что описывают на форуме как «задумка».

**Как комнату `56` вообще удаётся сверить с картриджем.** Она не доживает
до следующей границы витка игры: `C4E3` → `C60D` снимает всю энергию и
убивает героя В ТОМ ЖЕ КАДРЕ, а мёртвый герой идёт мимо `C160`, поэтому на
первой же границе витка после неё в `GAME_VARS+0xC` уже комната возврата
(замер: `50`). Поэтому `tools/cmp_allrooms_msx.py` снимает состояние не на
границе витка, а НА ВХОДЕ В `C4E3`: комната уже нарисована целиком (теневой
буфер атрибутов заполнен, четвёрка соседей положена), а `C60D` ещё не
отработал. Так комната `56` попадает в сверку наравне с остальными
восемьюдесятью шестью.

### 7.4 Пламя — образы `0x24`/`0x25`, три штуки

Таблица `BCBA`, 3 записи по 3 байта (комната, X, фаза); обход — `BC58`.
Y низа зашит `0x58` (`BC89`). Кадр переключается каждый вызов (`BC91 xor 1`).
В ПОРТЕ (только полный образ) этот `xor 1` заменён чтением ячейки
`v_flame`: кадр меняется раз в 5 кадров = 100 мс, «как на MSX» — решение
владельца 2026-09-22, `docs/adapter-requirements.md` § 0b.

| комната | X |
|---|---|
| `27` | `98` |
| `51` | `18` |
| `53` | `50` |

Урон — `BCE1`: если X героя в `[X − 0x28, X + 0x1C]` и Y героя больше `0x28`,
`jp C92C` — **−1 деление за каждый кадр в огне**.

### 7.5 Падающая плита — образ `0x1E`, шесть штук, МГНОВЕННАЯ СМЕРТЬ

Таблица `BCC3`, 6 записей по 5 байт (комната, X, Y, таймер, Y исходный);
обход — `BBD5` (`ld b,0x06`).

| комната | X | Y | таймер |
|---|---|---|---|
| `0C` | `40` | `28` | `36` |
| `17` | `38` | `28` | `1B` |
| `19` | `60` | `20` | `1C` |
| `2D` | `50` | `20` | `35` |
| `30` | `40` | `28` | `4E` |
| `3F` | `38` | `20` | `67` |

Пока герой в этой комнате, `dec (iy+3)`; когда таймер обнулился — `BC25`:
проверить, есть ли опора под плитой (`C2D6`, `d = 0x40`); если нет — плита
падает на 4 пикселя за кадр, и тут же:

```
BC40  call C8F2 / xor a / cp e / ret z
BC46  jp C625                  ; ← СМЕРТЬ БЕЗ ВАРИАНТОВ
```

Это не потеря энергии, а мгновенная гибель. Фаза таймера разыгрывается
`ld a,r` (`BC0A`), так что предугадать момент нельзя — надо просто не стоять
под плитой.

### 7.6 Сводка «кто чем опасен»

| опасность | цена |
|---|---|
| призрак, горбун, оборотень (20 патрулей) | −1 энергии за кадр |
| набегающий зверь, стрела лучника | −1 энергии за кадр |
| пламя (3 места) | −1 энергии за кадр |
| падение выше 16 px | −(высота−15) энергии |
| свой выстрел | −1 энергии |
| **падающая плита (6 мест)** | **смерть сразу** |
| **касание орла** | **смерть сразу** |
| **тёмная комната `56`** | **вся энергия → смерть** |

## 8. «Уровни»: сколько их и что значит «следующий»

В коде есть `LEVEL_VARS` и `CE6A` («старт уровня»), но **прогрессии уровней
нет**. `BB89` — единственная точка «начать» — зовёт `CA3D`, а та делает всё
сразу:

```
CA3D  call CFCA / CD94 / DAE9 / CA0C / CF07   ; погасить, значки, панель, энергия, цвет
CA4F  call CE6A                                ; сброс рычагов + розыгрыш предметов
CA52  call C1FF                                ; ← 3 жизни, комната 00, X=40 Y=50
CA55  call CA8D                                ; персонажи на исходные места
CA58  очистить F2B9 (87 байт посещённых)
CA65  (CD42) := 0                              ; обнулить проценты
CA69  (LEVEL_VARS) := (LEVEL_VARS+1)           ; нижнее окно = комната шара
```

На `BB89` приходят оба конца игры — и победа (`BD2A`), и проигрыш (`BBD2`).
Значит **«следующий уровень» = та же игра сначала, с новым розыгрышем мест
трёх предметов** (один из 16 раскладов). Ни карта, ни враги, ни персонажи
не меняются.

**Клавиши `1`..`5` — это НЕ выбор персонажа** (как сказано в
`docs/v06-input-sound.md`), а выбор того, **что показывать в нижнем окне**
(§ 5.3). Игрок всегда один и тот же маг. Эту строку в `docs/v06-input-sound.md`
стоит поправить.

## 9. Клавиши — полный список

| действие | MSX | Вектор | адрес опроса |
|---|---|---|---|
| влево | `O` | `←` | `CC87` + таблица `CC95` |
| вправо | `P` | `→` | там же |
| вверх / прыжок / лезть вверх | `Q` | `↑` | там же |
| вниз / присесть / лезть вниз | `A` | `↓` | там же |
| молния | ПРОБЕЛ | ПРОБЕЛ | там же |
| **взять предмет** | SHIFT | **СС** | `C9BC` (строка 6, бит 0) |
| пауза | `H` | **ВК** | `D684`, `CC5D` (строка 3, бит 5) |
| смотреть: книга / жезл / принцесса / доспех / орёл | `1`..`5` | `1`..`5` | `BF8E` (строка 0, биты 1..5) |
| «любая клавиша» — выйти из титров и начать игру | любая | любая | `CFAD` (перебор строк `F0..F8`), выход `CF85` |
| «любая клавиша» на экране итога и в финале | любая | любая | `CC67`, `CFAD` |

Буквы `Q`/`A`/`O`/`P` на клавиатуре Вектора **не двигают** героя
(2026-09-24): раскладка Вектора другая, в тень MSX идут только курсоры
и джойстик (`src/v06/kbd.asm`).

Титры (`CF3E`) крутятся бесконечно (`CF89 jr CF63`), пока не нажать что
угодно; сразу после этого начинается игра — отдельного «меню» нет.

Джойстик (порт 2 на MSX) даёт тот же байт, что и клавиатура: порядок кодов в
`CC95` совпал с порядком битов джойстика (`docs/v06-input-sound.md`).

**Пауза на Векторе — ВК.** Строку 3 бит 5, которую опрашивает игра, кормит
клавиша ВК. Выйти из паузы по-прежнему можно любой клавишей, в том числе
повторным ВК.

### 9.1. Читы

Полное описание — `docs/cheats.md`. Коротко:

* **включить** — зажать **F1 + F3** во время титров или в момент нажатия
  старта и подержать первые три секунды игры (пока идут титры, окно
  открыто без срока). Режим живёт до конца партии;
* **G** — god mode: энергия не убывает, мгновенная смерть (орёл, плита,
  тёмная комната `56`) не срабатывает, жизни не теряются;
* **8 / 9 / 6 / 7** — перейти в соседнюю комнату вверх / вниз / влево /
  вправо, ровно по четвёрке соседей из записи комнаты (§ 2.2). Нет соседа
  (`0`) — ничего не происходит;
* **K** — перейти в комнату, показанную в нижнем («смотровом») окне, то
  есть туда, куда игрок только что посмотрел клавишами `1..5` (§ 4).

Переход делается **штатным путём игры** — тем же, каким герой уходит за
край экрана, — поэтому после «вверх» он может сразу провалиться обратно:
чит не спрашивает, есть ли наверху пол.

Пока F1 + F3 не нажаты, клавиши `G/6/7/8/9/K` не делают ничего: они не
попадают даже в тень клавиатуры, и игра их не видит.

## 10. Известные баги ZX-версии и есть ли они у нас

Источник претензий — тема zx-pk.ru «игра spirits»
(<https://zx-pk.ru/threads/3851-igra-spirits.html>, 3 страницы, читана
2026-09-22).

### 10.1 (а) Битый байт `#7DBD` — ДОКАЗАНО, что это данные, и у нас они целы

**Что утверждает форум.** Все дисковые/TR-DOS сборки сделаны с польского
крэка; в нём по адресу `#7DBD` лежит `#C6` вместо `#46`, отчего «полтергейст,
дубликаты объектов, телепортация, сброс в финале, сброс при взятии
шара/кристалла». Оригинальный кассетный TZX проходится нормально. Там же
байт разобран как код: «вместо `ld b,(hl)` стоит `add a,$15`».

**Что на самом деле.** Это не код, а **данные**, и разбор форума — следствие
того, что дизассемблер пошёл по таблице. Доказательство прямое:

1. `ref/zx/Spirits.tap` — блок `AG CODE 1`, загрузка `0x60E0`, 40736 байт.
   Байт по `0x7DBD` в нём — `0xC6`.
2. Тот же 33-байтовый контекст ищется в `ref/zx/Spirits.tzx` **только** с
   байтом `0x46` на этом месте (найден по смещению 22415). То есть наш TAP —
   как раз крэкнутая раздача, а TZX — оригинал. Это подтверждает и
   `ref/zx/SOURCE.md` (ранее байт был прочитан из памяти MAME).
3. **Таблица карт комнат MSX `8446..A79B` (9046 байт) лежит в ZX-версии по
   адресу `0x61A8` и совпадает с MSX БАЙТ В БАЙТ — 9045 из 9046.**
   Единственное расхождение во всей таблице — ровно `0x7DBD`
   (MSX `0x46` ↔ ZX-крэк `0xC6`).
4. `0x7DBD − 0x61A8 = 0x1C15`; `0x8446 + 0x1C15 = 0xA05B`. Это **байт `+3`
   записи комнаты `0x45` (69)**, адрес записи `A058`, её соседи
   `[40, 4A, 44, 46]` = вверх 64, вниз 74, влево 68, **вправо 70**, элементов
   `0x15` = 21.

Значит в крэке комната `45` при выходе вправо ведёт в комнату **`0xC6` = 198**.
Индексатор `D16C` (в ZX — его аналог) отсчитает 198 записей от начала таблицы,
убежит за её конец (`A79C`, начало банка цвета) и выдаст мусорный указатель:
мусорное число элементов, мусорные образы и координаты, мусорные соседи. Это и
есть «полтергейст, дубликаты объектов, телепортация» и последующий вылет.
Следующий байт после испорченного — `0x15` (число элементов), и именно он
превратил `46` в «`add a,$15`» на форумном дизассемблере.

Почему «сброс при взятии шара» выглядел связанным с предметом: комната `45`
(69) — **одна из 18 комнат, где может лежать предмет** (пара 16 таблицы
`CEAA`: комната `45`, X = `04`), и лежит он у самого левого края. То есть
игрок, пришедший за предметом в `45`, с большой вероятностью в ту же минуту
уходил вправо — и попадал в мусорную «комнату 198».

**У нас.** База порта — восстановленный оригинал MSX (`ref/msx/orig/*`),
сверенный с кассетным образом `ref/msx/Spirits-1987-TopoSoft-ES.tsx`
(`tools/verify_orig.py`), и в нём по `A05B` стоит **`0x46`** — правильное
значение, подтверждённое сверх того побайтовым совпадением всей таблицы с
оригинальным ZX TZX. Испорченная раздача в проекте физически есть
(`ref/zx/Spirits.tap`), но в порт она не входит: TAP используется только для
разметки блоков, рабочий образ — TZX (`ref/zx/SOURCE.md`).

Формулировка «бит 7 операнда» из постановки задачи подтверждается:
`0x46 xor 0xC6 = 0x80`. Но это **не** флаг «прямой/зеркальный вывод» (тот
живёт в байте `+0` элемента, а не в соседе) и не флаг «рычаг сработал»
(`C65D`/`C680`, тоже байт `+0` элемента). Здесь бит 7 просто испортил номер
комнаты.

### 10.2 (а, продолжение) Подбор предмета в порте

Механизм подбора у нас тот же, что в оригинале MSX: `C9B5`/`C9C6`/`C9D4`,
переходы из `JUMP_TABLE_CD88`; ни один из его байтов в порте не менялся
(гейты `verify_disasm`, `verify_orig`, `verify_v06`). Соответствие
«шар/птица/кристалл» из форумной терминологии:

| форум (ZX) | наш разбор (MSX) | образ |
|---|---|---|
| «шар» / «bola» | слот 0, ШАР | `0x18`, 16×16 |
| «кристалл» | слот 2, ЖЕЗЛ (стержень со звездой) | `0x19`, 24×8 |
| «экран с птицей» | ОРЁЛ, запись 2 `CBBF` | `0x2F`–`0x32` |

«Сброс при взятии шара» и «потеря жизни на экране с птицей» — это следствия
того же испорченного соседа: игра оказывалась в мусорной комнате.
У нас «потеря жизни у орла» — **штатное правило** (`C079` → `jp C625`,
§ 5.2), а не баг.

> **Прогон настоящего подбора на стенде** (встать в окно `X ± 4`, нажать
> «действие») — см. § 10.5.

### 10.3 (б) Тёмная комната с существом с огромными глазами

Найдена и разобрана полностью — § 7.3. Комната `56`, обработчик `C60D`,
картинка глаз `CAD5`/`GFX_B540`, снятие всей энергии `C61E`/`C622`, возврат
в комнату `52` с −1 жизнью. **Это задуманное поведение, а не баг**: комната
специально сделана без выходов (входов в неё три: вниз из `51`, вниз из `52`,
вправо из `55`). Форумная правка Transman'а («теперь там энергия тратится
всегда») чинила не игру, а взаимодействие с читом бесконечной энергии: без
чита `C92C` доводит счётчик до нуля и уводит на `C627`, а с читом счётчик не
падает и выход из комнаты не наступает.

### 10.4 (в) Порча рамки при потере жизни

Относится к трейнерам (версия Куликова и т. п.), которые дописывали свой код
в область, задевавшую вывод. **У нас читов и трейнеров нет** — порт собирается
из чистого оригинала, рамки/бордюра в смысле ZX на Векторе тоже нет (цвет
задаётся палитрой, `docs/adapter-requirements.md` § 0c). Пункт неприменим.

### 10.5 Что показал стенд: НАСТОЯЩИЙ подбор порт не ломает

Стенд — `vector06js` без графики, образ `build/port/spirits-port.rom`,
детерминированная случайность (`tools/det_rng.js`, `docs/determinism.md`),
скрипт прогона лежит вне репозитория (временная папка сессии).

**Подбор настоящий, а не запись флага снаружи.** Игра сама прошла весь путь
`12B5 → 12C6 → 12D4 → 12D9` (векторные адреса; MSX `C9B5 → C9C6 → C9D4 →
C9D9`): клавиша «действие» (`СС`) подавалась через штатную матрицу
клавиатуры `vector06js`, проверку окна `X ± 4` игра делала сама. Встреча с
предметом устраивалась переносом ПРЕДМЕТА к герою — правились только данные
уровня `LEVEL_VARS+1/+2` (`167C`/`167D`), состояние игры не трогалось.

**Прогон с подбором (seed 1):**

| | |
|---|---|
| подбор произошёл | итерация **413**, кадр 1630 |
| `12D4` (флаг ставит сама игра) | **1 раз** |
| `12D9` (обработчик значка/очков) | **1 раз** |
| флаг `LEVEL_VARS+7` (`1682`) | 0 → **1** |
| счётчик процентов `CD42` (`1642`) | 0 → **0x0F** |
| значок шара в панели (стр. 16..17, кол. 25..26) | 0 → **132 закрашенных пикселя** |
| выход PC за пределы кода | **нет** |
| перезапусков игры | **нет** |
| итераций игры ПОСЛЕ подбора | **327**, темп ровный (147…150 итераций на 500 кадров) |

**Смущало одно: за прогон жизни ушли 3 → 0.** Контрольный прогон тем же
расписанием, с тем же зерном, но БЕЗ переноса предмета и БЕЗ нажатия
клавиши (`12D4` = 0 раз) дал **тот же результат байт в байт**:

| | с подбором | контроль без подбора |
|---|---:|---:|
| `12D4` — код подбора пройден | 1 | **0** |
| итераций игры всего | 744 | **744** |
| потерь жизни (`CA7B`, MSX `CA7B`) | 3 | **3** |
| на каких итерациях | 217, 499, 743 | **217, 499, 743** |
| `C92C` — «энергия −1» | 141 | **141** |
| `C805` — касание патрульного врага | 410 | **410** |
| `BE63` — набегающий зверь | 24 | **24** |
| `BE36` — стрела лучника | 20 | **20** |
| `C1BE` — урон от падения | 9 | **9** |
| `C625` — **мгновенная смерть** | **0** | **0** |
| срыв PC | нет | нет |

**Вывод: жизни снимает расписание ходьбы, а не подбор.** Гибели —
исключительно от исчерпания энергии (`C92C` при нуле → `C627`, дальше
`CA7B`), а мгновенной смерти (`C625` — орёл, плита, тёмная комната) не было
ни разу. Источник урона — комната `00`, в которой стенд гоняет героя
туда-сюда: в ней стоит патрульный враг (запись 0 таблицы `B6A2`, комната
`0x00`), и расписание раз за разом ведёт героя прямо в него. Номера
итераций смертей совпадают с контролем **точно**; расходятся только номера
кадров последней смерти (2766 против 2738, разница 28 кадров) — это ровно
цена самого подбора: задержка показа «плюсика» очков (`CABF` → `C68A`) и
перезаливка полоски энергии (`CAD2` → `CA0C`).

**Повторено на другом зерне.** `SPIRITS_SEED=3`: подбор на итерации 417,
`12D4` = 1; контроль без подбора — `12D4` = 0. Оба прогона: **574** итерации
игры, **3** потери жизни на итерациях **129, 361, 573**, **290** касаний
патрульного, **141** списание энергии, `C625` — **0**, срыва нет. Числа
совпали полностью, расхождение опять только в кадре последней смерти
(2429 против 2433).

(На `SPIRITS_SEED=7` подбор не состоялся вовсе — клавиша нажималась
11 раз, но окно `X ± 4` не совпало и `12D4` осталось нулём. Как
доказательство «подбор не ломает игру» этот прогон не годится и в счёт не
идёт. Зато он показал, что сам стенд детерминирован: оба прогона seed 7
дали одинаковые **595** итераций, **3** смерти на итерациях
**273, 411, 594**, **399** касаний и **141** списание энергии.)

**Гейт закрыт:** настоящий подбор предмета в порте не сбрасывает игру, не
уводит PC, не теряет жизнь и не мешает игре идти дальше. Аналога бага
польского крэка ZX у нас нет — что и ожидалось из § 10.1, где доказано, что
испорченный байт был номером комнаты в карте, а наша карта совпадает с
оригиналом.

## 12. Сверка инструкции с кодом: где врёт и где молчит

### 12.1 Что подтвердилось дословно

| утверждение инструкции | подтверждение в коде |
|---|---|
| «экран разделён на две зоны с независимым действием» | `D184` + бит 7 (`C62E`/`C64A`), окна `00..5F` и `60..BF` |
| «в нижней (когда есть шар) — слежение, клавиши 1..5» | `BF83`: `ret z` по `LEVEL_VARS+7`, опрос `BF8E` |
| «пока шара нет, он сам появится в нижней зоне» | `CA69`: `(LEVEL_VARS) := (LEVEL_VARS+1)` = комната шара |
| «жезл власти — расколдовать принцессу» | `C088`: проверка `LEVEL_VARS+0xB` (слот 2 = жезл) перед записью 1 |
| «священная книга — расколдовать доспех» | `C09B`: проверка `LEVEL_VARS+9` (слот 1 = книга) перед записью 0 |
| «исполинский орёл, которого нужно уничтожить» | `C0AF` → `(BBD4) := 1` → `BCF6` (финал) |
| «прыгать, приседать, лезть по лестницам, метать молнии» | `C441`, `C27C`, `C4BB`, `C39F` |
| «рычаги, поднимающие решётки» | `C4E3`/`C65D`/`C680`, образ `0x36`, урезание счётчика `+5` |
| «горбуны, призраки, оборотни, демоны-лучники» | образы `0x10`–`0x12`, `0x13`–`0x15`, `0x0D`–`0x0F`, `0x22`/`0x23` |
| «карлики» | заколдованная принцесса — фигурка в колпаке, образы `0x2B`–`0x2D` |
| «два замка, соединённые между собой» | четыре взаимных нештатных перехода `18⇄28`, `1D⇄2B`, `2A⇄38`, `2D⇄3D` |
| джойстик в порту 2 | порядок кодов в `CC95` совпал с битами джойстика |

### 12.2 Где инструкция МОЛЧИТ (и это главные потери для игрока)

1. **Без шара книга и жезл вообще не появляются в комнатах.** Инструкция
   говорит только, что шар «покажет, где они лежат». На деле `C975` при
   невзятом шаре крутит цикл по одному слоту, и подобрать книгу раньше шара
   физически невозможно.
2. **Клавиши 1..5 мертвы без шара.** `BF83` выходит первым же `ret z`.
3. **Молния не убивает.** «Metar molnii» подано как оружие, а `BD42` только
   добавляет 50 кадров задержки. Единственная смертельная цель — орёл, и
   только после обоих расколдовываний.
4. **Касание орла убивает мгновенно** (`C079` → `jp C625`). Инструкция об
   этом не предупреждает вовсе.
5. **Три рычага открывают решётки в ДРУГИХ комнатах** (`0D`→`13`,
   `1F`→`1E`, `3D`→`3F` и `40`).
6. **Комната `56` — гарантированная смерть без выхода.**
7. **Шесть падающих плит убивают мгновенно** (`BC46 jp C625`).
8. **Свой выстрел стоит энергии** (`BE33`).
9. **Высокое падение стоит энергии** (`C1BE`).
10. **Жизней три, энергии 47 делений** — чисел в инструкции нет.
11. **Карты в игре нет.**

### 12.3 Где инструкция ВРЁТ (или описывает не то, что вышло)

| инструкция | код |
|---|---|
| «рычаги, что поднимают решётки **или включают ловушки**» | все 8 обработчиков только **убирают** элементы; кода, который рычагом бы что-то включал, нет. **Ловушек, включаемых рычагом, не найдено** |
| «котлы, полные бурлящего зелья» (в рассказе) | образ `0x2E` (чаша/котёл) существует, но используется как «особый» кадр принцессы (`iy+0x0A`), отдельным предметом не является |
| «свирепые воины» (в рассказе) | отдельного типа врага-воина нет; в игре 20 патрулей трёх видов + зверь + лучник |
| «Seguir Princesa» (следить за принцессой) на клавише **3** | верно, но в записи `CBBF` принцесса — **вторая** запись (`CBCC`), а доспех — первая; в таблице клавиш порядок «принцесса, доспех» перевёрнут относительно порядка записей. На игру не влияет |
| «SHIFT — Coger» подан как отдельное действие «взять» | это же самое и есть «действие у объекта»: другого применения у SHIFT в коде нет (`C9BC` — единственный опрос строки 6) |
| «два замка» | в данных мир — единая сетка 5 × 18; визуального деления на два замка в таблицах нет. **Предположение:** «два замка» — это верхняя и нижняя половины сетки, связанные четырьмя нештатными переходами |

Сверх инструкции найдено в сети (`ref/manual/SOURCE.md`, п. 8) несколько
пересказов, добавляющих мотив «злой колдун украл вещи у мага», имена
персонажей и «две части руны» для орла — **ни одно из этого в коде не
подтверждается**, это фантазии обзорщиков.

## 13. Оценка «вставить справку в игру»

Задача: короткая справка по-русски **на один экран** (32 знакоместа × 24
ряда), показываемая перед стартом или по клавише с титров.

### 13.1 Чем печатать

Готовый печатник уже есть — `CDF9` (`16F9`), `docs/render-paths.md` § C.6:

* вход: `hl` = поток кодов, `b` = **длина потока в байтах**, `de` = позиция
  (`d` = ряд 0..23, `e` = знакоместо 0..31);
* один печатный знак = **один байт**;
* код `< 0x20` = «пропустить N знакомест», курсор переносится по ширине 32
  (`CE19`);
* цвет печатник не трогает — красить надо отдельно, `CF28`.

Ограничение: `b` — один байт, значит **на один вызов не больше 255 байт
потока**. Экран на 440 знаков потребует **двух вызовов** — это 10 лишних
байт кода, не проблема.

Готовый образец «экран текста с нуля» уже есть в игре — `CC0D` (экран
итога): `call CFCA` (погасить), `hl=0x6000 bc=0x181F a=цвет / call CF28`
(залить цвет всего экрана), `call CDF9`, и `CFAA` — ждать клавишу.
Код-обвязка справки — около **25 байт**.

### 13.2 Шрифт — кириллица уже есть

Это самая приятная часть оценки: **кириллица в проекте уже сделана**
(`docs/i18n-ru.md`, стадия сборки `tools/i18n_ru.py`, перевод утверждён
владельцем 2026-09-22). Состояние на сегодня:

* 11 букв (`А В Е К М Н О Р С Т Х`) отданы кодам латинских двойников;
* 22 буквы дорисованы: 9 сели в мёртвые коды `0x67..0x6F`
  (альт-логотип 1986), 13 приписаны за конец таблицы кодами `0x76..0x82`;
* база `FONT_BASE = 9BE2` (Вектор) **не переезжала**; новые глифы лежат в
  хвосте невидимой плоскости, `9F12..9F59` и `9F8A..9FF1`.

Значит **29 букв текста справки уже есть, доплачивать за них нечего**.
Латиница `A H O P Q` и цифры `1 5 7 8` тоже на месте.

**Чего не хватает — ровно трёх знаков: `.` `,` `-`** (двоеточие `:` = `0x72`,
пробел `0x73`, процент `0x74` уже есть). Это **24 байта** глифов.

И вот тут упирается в место: при нынешней базе `9BE2` глиф кода `c` лежит
по `9BE2 + (c−1)·8`, то есть код `0x83` → `9FF2..9FF9`, а код `0x84` уже
пересекает `A000` — начало экранной плоскости. **Свободен ровно один
код, `0x83`.** Три знака препинания без переезда шрифта не влезают.

Выходов два:

* **переставить шрифт на `407E`** — путь уже реализован и проверен
  (`tools/i18n_ru.py --font-addr 0x407E`, одна строка `FONT_RU_ADDR` в
  `tools/build_v06_rom.py`): вся таблица `0x21..0x82` = 98 глифов = **784
  байта**, правятся два операнда базы. Плюс три знака препинания
  (`0x83..0x85`) = **808 байт**. **Но `407E..49FF` свободна только после
  слияния с этапом E** — в дереве `native-fills` там живут теневые таблицы
  спрайтов, и резидентный слой заливает `40FE..48FD` нулями каждый кадр
  (`docs/i18n-ru.md` § 2);
* **обойтись одним новым знаком** — взять код `0x83` под точку, а запятую
  и тире из текста убрать. Текст § 13.3 при этом надо переписать; на
  читаемость это влияет, но не смертельно.

### 13.4 Куда положить — два варианта

**Вариант A (рекомендуемый): `407E..49FF`, вместе с переехавшим шрифтом.**
Возможен **после слияния с этапом E** — тогда эта зона доказанно мертва
(`tools/trap_stale_v06js.js`: за 3000 кадров код игры читал её 0 раз и
писал 0 раз).

| статья | байт |
|---|---:|
| свободно в `407E..49FF` | 2434 |
| вся таблица шрифта после переезда (98 глифов) | −784 |
| три знака препинания `. , -` (коды `0x83..0x85`) | −24 |
| поток справки | −462 |
| код-обвязка | −25 |
| **остаётся свободно** | **1139** |

Плюсы: текст жив всё время работы игры — справку можно показывать и по
клавише с титров, и повторно, сколько угодно раз. Запас остаётся больше
килобайта.

**Вариант B: в области, которую игра сама затирает.**

Заставочная мелодия уже кладётся в копии образов спрайтов `6100..655F`
(1120 байт), которые игра затирает после старта
(`docs/adapter-requirements.md` § 0b): партитура ≈450 + таблица нот 192 +
плеер ≈200 = **≈842 байта занято, свободно ≈278**. Полный текст § 13.3 туда
**не влезает**. Влезет сокращённый вариант:

```
  2    7  SPIRITS - СПРАВКА
  5    1  НАЙДИ ШАР - ОН ПОКАЖЕТ ВНИЗУ,
  6    1  ГДЕ КНИГА И ЖЕЗЛ.
  8    1  С КНИГОЙ КОСНИСЬ ДОСПЕХА,
  9    1  С ЖЕЗЛОМ - ПРИНЦЕССЫ,

 13    1  O P ИДТИ  Q ПРЫЖОК  A СЕСТЬ
 14    1  ПРОБЕЛ МОЛНИЯ  СС ВЗЯТЬ
 15    1  H ПАУЗА  1..5 СМОТРЕТЬ ВНИЗУ
 18    1  МОЛНИЯ ГЛУШИТ И ЕСТ ЭНЕРГИЮ.
 19    1  ОРЕЛ УБИВАЕТ КАСАНИЕМ.
```

260 знаков + 17 кодов пропуска = **277 байт потока**, один вызов `CDF9`
(≤ 255) уже не проходит — нужны два, обвязка ≈ 20 байт. Итого ≈ 297 байт при
278 свободных: **не влезает на 19 байт**, придётся либо резать две строки,
либо ужимать партитуру. Шрифт при этом остаётся там, где он сейчас
(`9F12..9FF1`), и знак препинания доступен только один — код `0x83`.

Плюс варианта B: не трогает ни `407E..49FF`, ни базу шрифта, то есть не
ждёт слияния с этапом E. Минусы: (1) справку можно показать **только один
раз, до старта игры** — после старта байты затёрты, и клавиша «справка» с
титров второй раз ничего не покажет; (2) текст придётся писать почти без
знаков препинания; (3) выигрыша по памяти нет — в варианте A после всех
расходов остаётся ещё 1139 свободных байт.

**Образ порта с заставкой занимает `A000..FFFF`** (`docs/v06-memory.md`), то
есть свободного места «под экраном» там нет — рассматривались только две
области выше.

### 13.5 Где показывать

Как устроен старт: `82E8 jp BB89`, `BB89 call CF3E`. `CF3E` — это и есть
экран титров: гасит экран, красит ряды 9/10/11, включает XOR-печать и
**крутит шесть строк кредитов по кругу** (`CF63`…`CF89 jr CF63`), пока
`CFAA` не вернёт «нажата клавиша» (`CF85 jr nz,CF8B`). После выхода
управление сразу уходит в `CA3D` — новая игра. То есть врезаться можно в
двух местах:

1. **Один раз перед стартом** — между `CF3E` и `CA3D` (три байта на
   `call` в `BB8C`): погасить, напечатать справку, `call CFAA` (ждать
   клавишу), вернуться. Самое дешёвое, работает в обоих вариантах
   размещения.
2. **По отдельной клавише с титров** — `CFAA`/`CFAD` перебирает строки
   `F0..F8` и выходит по любой клавише; после `CF85` уже известно, что
   что-то нажато, и можно одним опросом (как в `CC5D` для `H`) отличить
   «справка» от «играть». Требует **варианта A**: текст должен быть жив
   всё время, потому что после первой игры область варианта B затёрта.

**Решение — за владельцем.**

## 14. Что осталось непроверенным

* Закрыты ли стенами «заворотные» переходы из колонки 4 в колонку 0
  следующего ряда (§ 2.3) — по данным они существуют, по картинке не
  проверено.
* Достижимы ли все 87 комнат при реальной геометрии — арифметически граф
  связен, но рычаги и полы могут часть отрезать. Отсюда и вопрос, достижимо
  ли на практике слагаемое «21» в проценте.
* Ловушки, «включаемые рычагами», из инструкции — в коде не найдены;
  возможно, не вошли в игру.
* Что именно делают 8 байт `CEFE..CF05`, копируемые в `0x7F9C` (`CE83`):
  читателей этого адреса в живом коде нет.
* Подбор на стенде проверен только для **слота 0 (шар)**. Слоты 1 и 2
  (книга, жезл) идут теми же тремя инструкциями `C9B5`/`C9C6`/`C9D4` и
  отличаются только адресом обработчика из `JUMP_TABLE_CD88`, но прогоном
  это не показано.
